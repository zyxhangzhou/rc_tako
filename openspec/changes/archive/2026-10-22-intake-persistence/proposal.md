# Proposal

## Why

业务系统把通知交给本服务以后就不再等结果，所以本服务需要一个明确的责任交接点：通知写入存储之后，才返回"已受理"。在这之前，丢失由业务方负责（业务方重试）；在这之后，由本服务负责。没有这个交接点，后续的投递引擎（change B）就无法兑现"至少一次"。

## What Changes

- 新建 Python 项目骨架，包括服务入口、配置和测试框架。
- 新增提交接口，接收 url、method、headers、body、可选的过期时间和幂等 key。只有持久化成功才返回受理成功并带上通知 ID，否则返回错误。
- 调用方认证：每个业务系统持有一个 token，凭 token 识别是谁提交的。
- 输入校验：scheme 只允许 http/https；method 限定在白名单内；body 不超过 1MB。
- 受理侧地址防护：拒绝解析后 IP 属于私网、回环、链路本地或元数据地址的目标。
- 幂等去重：同一调用方用同一个幂等 key 重复提交时，返回已有的通知 ID，不新建通知。
- 通知以"待投递"状态持久化，进程重启后不丢失。本 change 不包含投递。

## Capabilities

### New Capabilities

- `notification-intake`：提交接口的对外契约，包括调用方认证、输入校验、受理侧地址防护、幂等去重，以及"受理成功就意味着已持久化"这一保证。
- `notification-store`：已受理通知的持久化，包括状态模型的起点（待投递）和重启后不丢失。投递引擎会在此基础上扩展状态流转和占用。

### Modified Capabilities

（无。仓库目前没有已有 spec。）

## Impact

- **代码**：新建整个 Python 项目，目前仓库里没有代码。
- **API**：新增提交接口，这是业务系统接入本服务的唯一入口。
- **依赖**：引入 Web 框架和存储依赖，具体选型在 design.md 里给出推荐方案和替代方案，由候选人拍板。
- **对后续 change 的约束**：存储选型决定了 B 里"带期限的占用"和"持久化的重试时间"怎么实现。
