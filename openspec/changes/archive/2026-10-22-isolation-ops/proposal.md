# Proposal

## Why

B 完成后，投递语义已经具备，但还有两个缺口：

- **隔离**：一个持续超时的下游最多能占满全部 16 个投递线程，导致其他下游也一起受阻。阶段 1 把"一个下游挂掉不应拖慢其他下游"列为隐含需求，这是 B 已知局限中最大的一个。
- **运维**：进入失败终态的通知，目前只能直接查库，无法补救。阶段 1 定下的承诺是"终态可查询、可人工重放、可观测"，这一部分还没有兑现。

## What Changes

- 按目标 host 限制同时投递的数量，默认每个 host 最多 4 条，可配置。限制在取任务时生效，状态保存在存储中，worker 重启后依然有效。
- 新增 `GET /notifications/{id}`：只有提交方本人可以查询。返回状态、失败原因、时间信息、每次尝试的记录，以及原始请求；其中 Header 按白名单脱敏。
- 新增 `POST /notifications/{id}/replay`：只有提交方本人可以操作。把处于失败终态的通知改回待投递，沿用同一个通知 ID，并从重放时刻重新计算重试窗口。原因为"已过期"的通知、已经超过 `expires_at` 的通知、已送达或尚未进入终态的通知，一律拒绝。
- 新增 `GET /metrics`，输出 Prometheus 文本格式：各状态的通知数、积压量、最老一条待投递通知的等待时长、各失败原因的数量、各结果分类的尝试次数。数值全部从存储中统计。

## Capabilities

### New Capabilities

- `notification-query`：提交方查询单条通知的投递状态和尝试记录，包括访问控制和 Header 脱敏规则。
- `notification-replay`：提交方对处于失败终态的通知发起人工重放，包括哪些通知可以重放，以及重放后的投递语义。
- `service-metrics`：对外暴露投递相关的运行指标。

### Modified Capabilities

- `notification-delivery`：
  - 新增需求：按目标 host 限制同时投递的数量。
  - 修改需求"重试期限与过期进入终态"：重试窗口的起点由"受理时间"改为"受理时间或最近一次重放的时间"。

## Impact

- **代码**：
  - 存储层追加 schema v3：新增 `target_host`、`retry_window_start` 两个字段。
  - `claim_due` 加入按 host 的并发上限。
  - `policy.deadline` 改为从重试窗口起点开始计算。
  - API 新增三个端点。
- **依赖**：不新增。指标输出手写 Prometheus 文本格式。
- **运维**：`/metrics` 不需要认证，因为它只暴露计数，不包含通知内容。
