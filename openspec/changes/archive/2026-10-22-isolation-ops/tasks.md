## 2. 按 host 限流

- [x] 2.1 新增配置 `NOTIFIER_WORKER_PER_HOST_LIMIT`，默认 4，取值必须在 1 到 `concurrency` 之间，超出范围时报错。补充配置的单元测试。
- [x] 2.2 `claim_due` 增加 `per_host_limit` 参数，按 design D1 写成 CTE 加窗口函数的查询。存储层测试覆盖三种情况：
  - 同一 host 有 10 条到期通知、上限为 4 时，只取出 4 条；投递中的数量降下来后，可以继续补取。
  - 两个 host 混在一起时，各自独立计算上限。
  - 占用已过期的通知不计入该 host 的并发数。

  [场景"同一 host 不超过上限"、"占用过期的通知不占名额"]
- [x] 2.3 隔离效果的集成测试，使用真实的 `Worker.run()` 线程，并发数 4、每个 host 上限 2：
  - 下游 X 每个请求都阻塞，直到测试结束，并预先放入 10 条通知。
  - 下游 Y 立即返回 200，放入 5 条通知。
  - 断言：Y 的 5 条通知在 3 秒内全部送达；X 同时收到的请求数始终不超过 2。

  [场景"慢下游不拖累其他下游"]

## 3. 查询接口

- [x] 3.1 在存储层新增"按调用方读取通知"的函数（调用方不匹配时返回 None），以及 Header 脱敏函数（白名单，比较时不区分大小写）。单元测试覆盖：白名单内的 Header 显示原值；X-Api-Key、authorization 等其他 Header 替换为 `***`；原始数据不被修改。
- [x] 3.2 实现 `GET /notifications/{id}`，用 TestClient 覆盖以下场景：
  - 先 500 后 200 的通知：查询结果为已送达，并有 2 条尝试记录。注意 worker 投递需要放开地址校验，所以测试数据直接写入存储，并用测试专用的 guard。
  - 等待重试中的通知：结果里带 `next_attempt_at`。
  - 因 400 失败的通知：失败原因为永久失败。
  - 查询他人的通知、查询不存在的通知：都返回 404。
  - 不带认证：返回 401。
  - Header 已脱敏，同时下游实际收到的仍是原值。

  [需求"查询单条通知"、"查询的访问控制"、"查询结果中的 Header 脱敏"]

## 4. 重放接口

- [x] 4.1 存储层实现 `replay(conn, id, caller, now_ms)`：用一条条件 UPDATE 完成状态检查和修改，返回 `replayed`、`not_found` 或 `not_replayable` 之一。单元测试覆盖：
  - 可以重放：永久失败、重试耗尽、目标被禁止。
  - 不能重放：已过期、已超过 `expires_at`、已送达、待投递、投递中。
  - 他人的通知返回 `not_found`。
  - 8 个线程同时重放同一条通知，只有 1 个成功。

  [需求"不可重放的情况" / 场景"并发重放"]
- [x] 4.2 实现 `POST /notifications/{id}/replay`，状态码为 202、404、409、401。用 TestClient 加 worker 测试以下场景：
  - 400 失败后，修正下游再重放：最终为已送达，两次请求的 `X-Notification-Id` 相同，`X-Notification-Attempt` 依次递增。重放前已经尝试过 2 次的，重放后那次的序号为 3。
  - 重试耗尽后重放：重新获得完整的重试期限。
  - 409 和 404 的各种情况，并确认这些情况下通知状态没有变化。

  [需求"重放失败的通知"、"不可重放的情况"、"重放的访问控制"]
