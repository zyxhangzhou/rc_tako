# Spec Delta

## Purpose

定义已受理通知的投递语义：至少一次送达、失败如何分类、何时重试、何时进入终态，以及系统向下游承诺透传的去重依据。

## ADDED Requirements

### Requirement: 仅在收到 2xx 后标记已送达
系统 MUST 只在目标返回 2xx 响应后，才把通知标记为"已送达"。在得到 2xx 之前，通知 MUST 一直处于"待投递"或"投递中"，或者进入失败终态，不能被视为已完成。

#### Scenario: 首次投递成功
- **WHEN** 一条待投递通知的目标返回 200
- **THEN** 该通知的状态变为"已送达"，并且不会再被投递

#### Scenario: 先失败后成功
- **WHEN** 目标第一次返回 500，第二次返回 200
- **THEN** 该通知最终为"已送达"，目标一共收到 2 次请求

### Requirement: 结果不明时重新投递
对于请求已经发出、但系统没有得到明确响应的情况（请求超时、请求发出后连接中断、投递进程在记录结果之前崩溃），系统 MUST 视为未送达并重新投递，哪怕这会导致下游收到重复请求。

#### Scenario: 下游已处理但响应超时
- **WHEN** 目标处理了请求，但响应时间超过单次请求超时
- **THEN** 系统会再次投递该通知，下游会收到两次带相同通知 ID 的请求

#### Scenario: 投递进程在请求发出后崩溃
- **WHEN** 投递进程已经发出请求，但在记录结果之前被强制终止，随后重启
- **THEN** 占用期限过后，该通知会被重新投递，最终状态为"已送达"

### Requirement: 透传稳定的通知 ID
系统 MUST 在每次投递请求中携带 `X-Notification-Id` Header，值为受理时分配的通知 ID，同一条通知的所有尝试都相同。系统 MUST 同时携带 `X-Notification-Attempt` Header，表示这是第几次尝试，从 1 开始。这两个 Header 的值由系统决定，会覆盖提交时 headers 里的同名项。

#### Scenario: 重试时 ID 不变
- **WHEN** 一条通知被投递了 3 次
- **THEN** 3 次请求的 `X-Notification-Id` 都等于该通知的 ID，`X-Notification-Attempt` 依次为 1、2、3

#### Scenario: 原样发送提交的请求
- **WHEN** 一条通知被投递
- **THEN** 目标收到的 method、url、body，以及提交时的 headers，都与提交时一致

### Requirement: 失败分类
系统 MUST 按以下规则对投递结果分类：
- 3xx，以及除 408、429 之外的 4xx：永久失败，直接进入失败终态，不再重试。
- 5xx、408、429、请求超时、连接错误、DNS 解析失败：临时失败，安排重试。

系统 MUST NOT 跟随重定向。

#### Scenario: 400 不重试
- **WHEN** 目标返回 400
- **THEN** 该通知进入失败终态，原因为永久失败，目标只收到 1 次请求

#### Scenario: 重定向不跟随
- **WHEN** 目标返回 302，并带有 Location
- **THEN** 系统不会请求 Location 指向的地址，该通知进入失败终态，原因为永久失败

#### Scenario: 429 进入重试
- **WHEN** 目标返回 429
- **THEN** 该通知回到"待投递"，并安排了下一次重试时间

#### Scenario: 连接被拒绝时进入重试
- **WHEN** 目标端口无人监听，连接被拒绝
- **THEN** 该通知回到"待投递"，并安排了下一次重试时间

### Requirement: 退避重试且计划持久化
系统 MUST 以指数退避安排临时失败后的重试：首次间隔约 10 秒，之后每次翻倍，单次间隔不超过 1 小时，并带有随机抖动。目标响应中带有 Retry-After 时，系统 MUST 按它安排下一次重试，但同样不超过 1 小时。下一次重试时间 MUST 持久化，投递进程重启后，不得提前投递，也不得把退避进度重置。

#### Scenario: 遵守 Retry-After
- **WHEN** 目标返回 503，并带有 `Retry-After: 120`
- **THEN** 下一次重试时间约为 120 秒之后

#### Scenario: 重启后不提前重试
- **WHEN** 一条通知已经失败 3 次，下一次重试安排在 80 秒之后，此时投递进程重启
- **THEN** 在原定的重试时间之前，该通知不会被投递

#### Scenario: 间隔逐次增长
- **WHEN** 目标持续返回 500
- **THEN** 相邻两次尝试的间隔逐次增长，直到达到上限

### Requirement: 重试期限与过期进入终态
每条通知的截止时间，取"受理时间 + 最大重试时长（默认 24 小时，可配）"与 `expires_at` 中较早的那个。每次发送前，系统 MUST 检查截止时间；已到截止时间时，MUST NOT 发送，并把通知置为失败终态：重试期限先到，原因为重试耗尽；`expires_at` 先到，原因为已过期。按正常规则算出的下一次重试时间如果不早于截止时间，系统 MUST 改为在截止时间把通知置为失败终态，不再发请求。

#### Scenario: 重试耗尽
- **WHEN** 目标持续返回 500，直到超过最大重试时长
- **THEN** 该通知进入失败终态，原因为重试耗尽，之后不再投递

#### Scenario: 已过期不再发送
- **WHEN** 一条通知在等待重试期间超过了它的 `expires_at`
- **THEN** 系统不再向目标发送它，该通知进入失败终态，原因为已过期

#### Scenario: 下一次重试晚于过期时间
- **WHEN** 10:00 投递失败，按正常规则下一次重试应在 10:10，而该通知的 `expires_at` 为 10:05
- **THEN** 10:00 时该通知仍处于"待投递"，不会被提前标记为已过期；此后不会再发出请求；在 10:05 之后的一个轮询周期内，它进入失败终态，原因为已过期

#### Scenario: 截止时间前不提前重试
- **WHEN** 按正常规则算出的下一次重试时间晚于截止时间
- **THEN** 系统不会为了在截止时间前再试一次而把重试时间提前

### Requirement: 投递前校验目标地址
系统 MUST 在每次发送前重新解析并校验目标地址，校验规则与受理时相同。目标解析到被禁止的地址时，系统 MUST NOT 发送，并把通知置为失败终态，原因为目标被禁止。如果解析失败或超时，系统 MUST 按临时失败处理。

#### Scenario: 受理后 DNS 改为指向内网
- **WHEN** 一条通知受理时目标域名解析到公网，投递时却解析到 `10.0.0.5`
- **THEN** 系统不发送，该通知进入失败终态，原因为目标被禁止

#### Scenario: 投递时 DNS 解析失败
- **WHEN** 投递时目标域名无法解析
- **THEN** 该通知回到"待投递"，并安排了下一次重试时间

### Requirement: 记录每次投递尝试
系统 MUST 为每次实际发出的投递尝试保存一条记录，内容包括：尝试序号、开始时间、耗时、结果分类、HTTP 状态码或错误描述，以及响应体的前 1KB。

#### Scenario: 尝试记录
- **WHEN** 一条通知先收到 500，再收到 200
- **THEN** 该通知有 2 条尝试记录，按顺序分别记有状态码 500 和 200
