# Proposal

## Why

change A 已经保证"受理即已持久化"，但还没有投递，已受理的通知只会停在"待投递"。本 change 要兑现阶段 1 定下的承诺：已受理的通知会持续投递，直到成功、判定为永久失败，或超出重试期限或过期为止。语义是至少一次（规则 2–6，见 change-plan v1 的 Background 一节）。

## What Changes

- 新增投递 worker，从存储中以带期限的占用方式取出到期的通知，向目标发出 HTTP 请求。
- 只有收到 2xx 才标记"已送达"。超时、连接错误，以及在请求发出之后崩溃，都按"结果不明"处理并重试，可能导致重复送达。
- 失败分类：
  - 永久失败，直接进入终态：3xx，以及除 408 和 429 以外的 4xx。
  - 临时失败，进入重试：5xx、408、429、超时、网络错误、DNS 解析失败。
  - 遵守 `Retry-After`。
- 指数退避，下一次重试时间持久化，进程重启后继续按原计划执行，退避不会被重置。
- 进入终态的条件：永久失败；从受理算起超过重试期限（默认 24h，可配）；超过调用方提交的 `expires_at`。
- 每次投递都带上相同的通知 ID Header，供下游去重。
- 不跟随重定向；单次请求超时默认 10s，可配。
- 投递时再做一次地址校验：目标解析到内网或元数据地址时，判定为永久失败。
- 每次投递尝试都留一条记录（时间、结果、状态码或错误），供排障和 change C 的查询接口使用。

## Capabilities

### New Capabilities

- `notification-delivery`：已受理通知的投递语义，包括至少一次、失败分类、退避重试、终态判定、通知 ID 透传、投递侧地址校验和投递尝试记录。

### Modified Capabilities

- `notification-store`：新增需求。通知的状态从"待投递"扩展为"投递中"、"已送达"、"失败（终态）"；每条通知持久化下一次重试时间和占用期限；保存投递尝试记录。已有的需求不变。
- `notification-intake`：修改需求"拒绝内网与元数据目标地址"。受理时 DNS 解析超过 2s，按"解析失败"处理，照常受理，避免 DNS 变慢直接拖长受理延迟。

## Impact

- **代码**：新增 worker 模块和 HTTP 客户端封装；存储层追加 schema v2，新增状态、调度字段和尝试记录表。
- **依赖**：HTTP 客户端使用 httpx，它已是测试依赖，这里提升为运行时依赖。
- **运行方式**：worker 的进程模型（和 API 同进程还是独立进程）由 design 决定，README 的运行说明会随之更新。
- **对 C 的约束**：worker 取任务时要预留"按目标分组"的扩展点；尝试记录的结构就是 C 查询接口的数据来源。
