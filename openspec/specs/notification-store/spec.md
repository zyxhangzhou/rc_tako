# notification-store Specification

## Purpose
保存已受理的通知（投递所需的完整请求内容、提交方、幂等 key 与状态），保证它们在服务进程正常退出或被强制终止后仍然完整可用，为投递引擎提供可靠的数据来源。

## Requirements

### Requirement: 完整保存投递所需内容
系统 MUST 为每条已受理的通知保存投递所需的全部内容：url、method、headers、body、expires_at，以及通知 ID、提交方、幂等 key 和受理时间。保存的内容 MUST 与提交时一致，不能改写。

#### Scenario: 内容原样保存
- **WHEN** 一条带有自定义 headers 和 JSON body 的通知被受理
- **THEN** 按通知 ID 读出的 url、method、headers、body、expires_at 与提交时逐项一致

### Requirement: 新受理通知的初始状态
系统 MUST 把新受理的通知置为"待投递"状态。

#### Scenario: 初始状态
- **WHEN** 一条通知被受理
- **THEN** 它在存储中的状态是"待投递"

### Requirement: 重启后数据不丢失
系统 MUST 保证：已返回受理成功的通知，在服务进程正常退出或被强制终止后，重启时仍然存在，内容和状态都不变。这一保证的前提是存储介质本身没有损坏。

#### Scenario: 强制终止后重启
- **WHEN** 已受理若干条通知后，服务进程被 SIGKILL 终止，然后重新启动
- **THEN** 这些通知全部存在，状态仍是"待投递"，内容不变

#### Scenario: 首次启动
- **WHEN** 服务在一个没有数据文件的环境中启动
- **THEN** 系统自动初始化存储，并且能够正常受理通知

### Requirement: 投递状态模型
系统 MUST 用以下状态表示通知的投递进度：待投递（包括等待重试）、投递中（已被某次投递占用）、已送达（终态）、失败（终态）。处于失败状态的通知 MUST 记录失败原因，取值为以下之一：永久失败、重试耗尽、已过期、目标被禁止。终态的通知 MUST NOT 被投递进程再次取出。

#### Scenario: 终态不再被取出
- **WHEN** 一条通知已经处于"已送达"或"失败"状态
- **THEN** 投递进程不会再取出它

#### Scenario: 失败原因可见
- **WHEN** 一条通知因为目标返回 400 而失败
- **THEN** 存储中该通知的状态为"失败"，失败原因为"永久失败"

### Requirement: 带期限的占用
系统 MUST 以带期限的占用方式交给投递进程：同一时刻，一条通知最多只被一个有效占用持有；占用过期后，该通知 MUST 可以被重新取出。投递结果 MUST 只能由当前有效占用的持有者写回；持有已过期占用的旧投递，其结果 MUST 被丢弃。

#### Scenario: 占用过期后重新取出
- **WHEN** 一条通知被占用后，持有者在占用期限内没有写回结果
- **THEN** 占用期限过后，这条通知可以被再次取出

#### Scenario: 过期占用的结果被丢弃
- **WHEN** 旧持有者的占用已经过期，通知已被新的占用取出，此时旧持有者才写回"已送达"
- **THEN** 旧持有者的写回不生效，通知状态以新占用的结果为准

#### Scenario: 未到期的通知不被取出
- **WHEN** 一条待投递通知的下一次重试时间还在未来
- **THEN** 投递进程不会取出它

### Requirement: 旧数据升级后可继续投递
系统 MUST 在启动时自动把旧版本的存储升级到当前版本，并保持已受理的通知不变。升级前已经存在的待投递通知，升级后 MUST 能被立即取出投递。

#### Scenario: 从仅含受理数据的版本升级
- **WHEN** 服务在一个由旧版本创建、含有待投递通知的数据文件上启动
- **THEN** 升级完成后，这些通知的内容不变，并且能被投递进程立即取出
