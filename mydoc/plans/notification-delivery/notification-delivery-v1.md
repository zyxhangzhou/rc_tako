## 背景

需求：业务系统提交完整的 HTTP 请求（URL / Method / Header / Body），本服务负责异步、可靠地投递；业务系统不关心返回值。技术栈 Python。仓库目前没有代码。

阶段 1 定下的边界和承诺（AI 建议的处理记录见 docs/ai-review.md）：

- **透传边界**：本服务不理解各供应商的格式，也不托管凭证或做动态签名。有时效的签名在重试时会失效，这个局限已接受。
- **投递承诺**：通知一旦受理，就持续投递，直到出现三种结果之一：确认成功（2xx）、永久失败（4xx，408/429 除外）、超出重试期限（约 24h，可配）或过期。后两种进入终态，留有记录，可人工重放。
- **至少一次的规则**：
  1. 先落盘，再返回"已受理"。
  2. 收到 2xx 后才标记已送达。
  3. 用带期限的占用取出通知，占用过期后可重新取出。
  4. 重试计划持久化。
  5. 结果不明时按失败处理。
  6. 每次重试都带同一个通知 ID。
- **前提**：存储本身不丢数据（MVP 是单机）；业务方在没拿到受理回执时会自行重试，并带上幂等 key。
- **不保证顺序**，对业务的影响已记录。
- **目标地址防护只做最低限度**：拒绝私网、回环、链路本地及元数据地址。

本版的拆分原则：按"能独立验证的承诺"来切，不按功能点切。

### A — 受理与持久化

- **目标**：建立责任交接点，先落盘、再返回"已受理"（规则 1）。
- **范围（做）**：
  - 项目骨架。
  - 提交接口，字段为 url、method、headers、body、可选的过期时间、幂等 key。
  - 调用方 token 认证。
  - 校验：scheme 只允许 http/https；body ≤ 1MB；method 白名单。
  - 受理侧地址防护：解析后的 IP 不能落在私网、回环、链路本地或元数据地址。
  - 按幂等 key 去重。
- **范围（不做）**：投递逻辑。
- **验收**：
  - 受理返回后立刻杀进程，重启后数据仍在。
  - 同一个幂等 key 再次提交，返回同一个通知 ID。
  - 提交 `http://127.0.0.1` 或 `http://169.254.169.254` 会被拒绝。
- **备注**：存储选型是 A 的关键决策，候选人拍板后写入 design.md。这个选型决定了 B 里"带期限的占用"怎么实现。

### B — 投递引擎

- **目标**：落实规则 2–6、失败分类和终态。
- **范围（做）**：
  - worker 带期限占用地取出通知。
  - 单次请求超时 10s（可配）；不跟随重定向；每次请求都带同一个通知 ID 的 Header。
  - 失败分类：2xx 为成功；4xx（408/429 除外）为永久失败；5xx、超时、网络错误、429 进入重试，并遵守 Retry-After。
  - 指数退避，下一次重试时间持久化。
  - 重试满 24h（可配）或超过过期时间后进入终态。
  - 投递侧再次做地址校验（DNS 可能在受理之后发生变化）。
- **范围（不做）**：按目标隔离、查询、重放。
- **验收**（通过可控的假下游测试证明）：
  - 在"发出请求"和"记录结果"之间杀进程，重启后会重新投递。
  - 下游已处理但我方超时，下游收到两次，且两次的通知 ID 相同。
  - 先返回 500 再返回 200，最终状态为成功。
  - 返回 400 不重试，直接进入终态。
  - 持续返回 500 时，重启后退避节奏不会被重置，到期后进入终态。
  - 已过期的通知不再投递。
- **备注**：
  - 这是风险最高的 change。tasks.md 按规则和失败分类逐条设置验证关卡，每过一关就跑对应的测试。
  - worker 取任务时预留"按目标分组"的扩展点，方便 C 接入。
  - DNS rebinding 是否要严格防范（让校验用的 IP 和实际连接的 IP 一致），在 B 的 design.md 里评估。

### C — 隔离与运维

- **目标**：保证一个下游变慢不会拖累其他下游；终态的通知可查询、可重放、可观测。
- **范围（做）**：
  - 按目标 host 限制同时投递的数量。
  - 按通知 ID 查询状态和每次尝试的记录，返回时对 Header 脱敏。
  - 把终态通知重放回待投递状态。
  - 暴露指标：积压量、终态失败数、成功数。
- **范围（不做）**：管理 UI；对接告警系统。
- **验收**：
  - 下游 X 持续超时时，下游 Y 的投递延迟不受影响。
  - 终态通知重放后能投递成功。
  - 查询结果里看不到敏感 Header 的明文。
- **备注**：这是最可砍的 change。时间紧时只做查询和重放，按目标隔离写进"已知局限"。具体在 C 开始时决定。

## Out of scope

以下条目中，"候选人拍板"的已由你明确决定；其余是 AI 的建议，你已对整体内容确认。

- **凭证托管、动态签名、OAuth 刷新**：候选人拍板不做。做了会让系统必须理解供应商。
- **顺序保证**：候选人拍板不做。影响已记录在 docs/ai-review.md，需要保序的业务方自行携带版本号或事件时间。
- **按目标定制成功判定**：与透传边界冲突。"200 + 业务错误码"会被当作成功，作为已知局限写明。
- **投递结果回调业务方**：题目说明业务方不关心返回值。
- **供应商模板和格式转换**：属于透传边界之外。
- **exactly-once**：不可实现。只透传通知 ID，供下游自行去重。
- **熔断和主动探活**：退避重试已经起到限流作用。
- **批量提交和合并投递**：MVP 的量级用不上。
- **管理 UI**：API 已经够用。
- **业务侧事务一致性（outbox）**：属于业务方的责任，在 README 里写明。
- **多实例、高可用、多机房**：MVP 只做单实例，设计上不堵死扩展。
- **敏感数据加密存储**：MVP 只在查询和日志中脱敏，作为已知局限写明。
